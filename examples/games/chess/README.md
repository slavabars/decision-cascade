# Шахматы: движок предлагает, головы решают

Партия против Stockfish, в которой **наша обученная голова решает, когда
быстрому просчёту нельзя верить**. Это не «мы научили модель играть в шахматы»:
движок играет сильнее, а наш слой отвечает за другое — за цену решения.

![Демо: партия с эскалациями только там, где голова считает быстрый ответ ненадёжным](demo.gif)

*18 секунд из реальной записи: `need_deep` подсвечивает неуверенные позиции, на
них уходит глубокий просчёт. Партия этой записи — 1-0, 41 полуход, 6 эскалаций
(30%), 103 мс на наш ход.*

## Зачем это здесь

Проект про типизированные решения с честными вероятностями. Шахматы дают то,
чего нет в текстовых примерах: **замкнутый контур**, где каждое решение
проверяется исходом, а не разметкой.

Роли разделены явно:

| Кто | Что делает |
| --- | --- |
| Stockfish (`MultiPV 3`) | предлагает три лучших хода быстрым просчётом |
| голова `need_deep` (обучена на наших данных) | отвечает: надёжен ли быстрый ответ |
| каскад | при `need_deep ≥ порога` платим за глубокий просчёт, иначе берём быстрый ход |

Ход — типизированное решение (`Choice` из кандидатов), а `need_deep` — `Noul` с
вероятностью, которую можно сравнивать с ценой ошибки. Ровно то же, что в
тикетах: дешёвый путь по умолчанию, дорогой — по неуверенности.

## Установка

```bash
# Stockfish — официальный бинарник с GitHub, без sudo
bash examples/games/chess/fetch_engine.sh          # -> .tools/stockfish

# доска и легальность ходов (опциональный extra, в основную установку не входит)

# для записи GIF (необязательно): asciinema и agg как бинарники
# https://github.com/asciinema/asciinema/releases

```

## Полный цикл

```bash
# 1. данные: партии движка с самим собой, метка — расходится ли быстрый ответ
#    с глубоким. ~1600 позиций, 10-15 минут на 8 ядрах.
.venv/bin/python -m examples.games.chess.dataset \
  --engine .tools/stockfish --out-dir data/chess

# 2. головы: штатный рецепт проекта, никакого отдельного тренера
.venv/bin/python -m training.recipe.train_heads --specs chess --dataset data/chess \
  --encoder hash --dim 256 --train-steps 600 --out-dir checkpoints/packs/chess

# 3. температура: чтобы `need_deep` была вероятностью, а не логитом
.venv/bin/python -m training.recipe.calibrate_temperature --specs chess \
  --dataset data/chess --encoder hash --dim 256 \
  --checkpoint-dir checkpoints/packs/chess

# 4. оценка: качество против цены глубоких просчётов
.venv/bin/python -m examples.games.chess.evaluate \
  --pack checkpoints/packs/chess --data data/chess

# 5. партия
.venv/bin/python -m examples.games.chess.play \
  --engine .tools/stockfish --pack checkpoints/packs/chess --skill 0

# 6. запись демо в GIF
ENGINE=.tools/stockfish PACK=checkpoints/packs/chess \
  bash examples/games/chess/record.sh
```

## Что считается метрикой

`need_deep` предсказывает событие «быстрый ответ движка ненадёжен»: глубокий
поиск нашёл другой ход или сдвинул оценку больше чем на 50 сантипешек. Это
событие считается самим движком, поэтому разметка не требует человека и не
зависит от нашей шахматной силы.

Дальше два числа, которые имеют смысл:

- **качество** — доля позиций, где сыгранный ход совпал с глубоким ответом;
- **цена** — среднее время на ход.

Порог эскалации — это ручка между ними. «Всегда глубоко» даёт качество 1,0 за
полную цену; «всегда быстро» дёшево, но ошибается там, где позиция тактическая.

## Результаты

Датасет: 40 партий движка с самим собой, **1600 позиций** (960/320/320
train/val/test), доля «нужен глубокий» — 17%. Обучение — 600 шагов, `hash`-энкодер
на 256 признаков, температура подобрана на val (гейт «не навреди» её принял).

Голова предсказывает редкое событие, поэтому accuracy почти бесполезна: 0.822
при базовой доле 0.83. Смотреть надо на AUC и калибровку:

| Метрика (test, n=320) | Значение |
| --- | ---: |
| ROC-AUC | **0.819** |
| Brier | 0.117 |
| ECE (10 бинов) | **0.032** |
| Доля позиций, где быстрый ход совпал с глубоким | 0.83 |

Калибровка здесь не украшение: `need_deep ≈ 0.3` действительно означает «примерно
в трети таких позиций быстрый ответ подведёт», поэтому порог можно выбирать по
цене ошибки, а не на глаз.

## Цена против качества

`evaluate.py` на том же отложенном сплите (быстрый поиск 60 мс, глубокий 260 мс):

| Порог | Эскалаций | Качество | мс/ход |
| ---: | ---: | ---: | ---: |
| всегда быстро | 0% | 0.828 | 60 |
| 0.4 | 8% | 0.878 | 77 |
| **0.3** | **19%** | **0.912** | **98** |
| 0.2 | 42% | 0.963 | 143 |
| 0.1 | 55% | 0.988 | 169 |
| всегда глубоко | 100% | 1.000 | 260 |

Качество — доля позиций, где сыгранный ход совпал с ответом глубокого поиска.

Порог по умолчанию (0.3) закрывает **половину разрыва** между «всегда быстро» и
«всегда глубоко», потратив **38% цены** полного глубокого просчёта. Это и есть
продуктовая история каскада в одном числе: не «сильнее движка», а «почти та же
надёжность за меньшие деньги».

## Ограничения

- Это **не** обучение шахматам: кандидатов даёт движок, голова учится только
  предсказывать надёжность быстрого ответа. Сила игры ограничена движком.
- `hash`-энкодер по дискретным признакам — намеренно простой baseline. Он
  выдерживает конкуренцию с «всегда глубоко» только по цене, а не по качеству;
  на `gpt2` здесь смотреть нечего — состояние не текстовое по смыслу.
- Признаки сделаны так, чтобы не протекать: в них нет ничего из глубокого
  поиска, только то, что известно до решения (материал, фаза, разброс оценок
  кандидатов, шахи и взятия).
- Одна партия в демо — иллюстрация, а не измерение. Измерение — `evaluate.py`
  на отложенном сплите.
