# Публичный бенчмарк RouterBench (маршрутизация LLM)

Второй публичный адаптер после AG News — **RouterBench** (Hu et al., 2024,
[arXiv:2403.12031](https://arxiv.org/abs/2403.12031),
[`withmartian/routerbench`](https://huggingface.co/datasets/withmartian/routerbench)).
Это ~36k промптов из стандартных наборов (MMLU, GSM-8K, HellaSwag, MBPP,
WinoGrande, MT-Bench, ...), для каждого — оценка качества (0..1) и стоимость
ответа 11 разных LLM. Это не классификация тем, а **настоящая decision-задача**:
«стоит ли эскалировать запрос на более сильную (и дорогую) модель». Поэтому
набор подходит для честной доменной калибровки каскада.

Датасет — pickle-таблицы (`routerbench_0shot.pkl`, `routerbench_5shot.pkl`);
версия зафиксирована ревизией `ROUTERBENCH_REVISION`, чтобы числа были
воспроизводимы.

## Маппинг на типизированные вопросы

Берём три уровня моделей по стоимости:

| Уровень | Модель |
| --- | --- |
| `cheap` | `mistralai/mistral-7b-chat` |
| `mid` | `mistralai/mixtral-8x7b-chat` |
| `strong` | `gpt-4-1106-preview` |

Из оценок этих трёх моделей детерминированно выводятся все три типа решений:

| Вопрос | Тип | Метка |
| --- | --- | --- |
| `escalate` | `noul` | 1, если дешёвая модель не решила задачу полностью (`cheap < 1`) — триггер каскада |
| `route` | `choice` | уровень с максимальным качеством; при равенстве — самый дешёвый (`cheap`/`mid`/`strong`) |
| `benefit` | `score` | выигрыш сильной модели над дешёвой (`strong - cheap`): `none`/`some`/`large` |

Правила описаны рядом с `_escalate_label`, `_route_label`, `_benefit_label` в
`eval/datasets/routerbench.py`. Промпт (`str`-представление списка сообщений)
разворачивается в текст состояния функцией `parse_prompt`.

Готового train/test в датасете нет, поэтому разбиение детерминированное (по
`seed`) и берётся из перемешанного порядка (случайная подвыборка, а не срез по
`eval_name`). По умолчанию `test_fraction = 0.25`.

## Материализация

```bash
.venv/bin/python -m eval.datasets.routerbench --out-dir data/routerbench --limit 6000
# train: 6000 -> data/routerbench/train.jsonl
# test : 1500 -> data/routerbench/test.jsonl
```

```bash
DECISION_MAX_LENGTH=256 .venv/bin/python -m eval.report.run \

  --train-steps 600 --device cuda --limit 4000 \
```

## Честная оговорка

Маршрутизация — **трудная** задача, и результат это подтверждает:

- `escalate` выходит примерно на **базовую частоту класса** (~0.79): голова
  ловит распространённость эскалаций, а не сам сигнал. Brier ≈ 0.213 против
  `p(1-p) ≈ 0.166` у константного предиктора базовой частоты — то есть навыка
  сверх «всегда эскалировать» почти нет.
- `route` (3 класса, chance ≈ 0.333) и `benefit` дают **небольшой** прирост над
  majority-классом.
- Увеличение выборки и шагов (`--limit 16000 --train-steps 1500`) качество
  `escalate`/`route` **не улучшает** — узкое место в заморожённых признаках, а не
  в объёме данных.

Вывод: RouterBench ценен как честный публичный бенчмарк (`accuracy < 1.0`, а не
`1.000` на синтетике) и как проверка калибровки, но заморожённый gpt2 с линейными
головами — не потолок качества.

## Что проверено: энкодер и дообучение

Оба подозрения из оговорки выше измерены на одном test-сплите (n=1000) с
несколькими сидами. Разбиение: `--limit 4000 --val-fraction 0.1`, то есть
train 3600 / val 400 / test 1000.

### Смена энкодера ничего не даёт

Головы те же (линейные), меняется только замороженный энкодер; по 5 сидов
обучения голов:

| Энкодер | Сиды (test acc) | mean ± sd |
| --- | --- | --- |
| gpt2 124M | 0.575 / 0.478 / 0.573 / 0.538 / 0.589 | **0.551 ± 0.040** |
| bert-base 110M | 0.587 / 0.585 / 0.576 / 0.505 / 0.519 | **0.554 ± 0.035** |

Разница +0.4 п.п. — внутри разброса по сидам. Это же объясняет прежние +1.9 п.п.
от bert: одиночный прогон. Заодно видно, что у заморожённых признаков разброс
огромный (±4 п.п.), то есть выбор одного удачного сида легко выдаёт шум за
улучшение.

### Дообучение энкодера — работает

`training/recipe/finetune_encoder.py` дообучает энкодер вместе с головами
(300 шагов, bert lr 5e-5, gpt2 lr 1e-4), затем головы оцениваются на том же
test:

| Вариант | Сиды | mean ± sd | `route` | `benefit` | `escalate` |
| --- | --- | --- | --- | --- | --- |
| замороженный gpt2 | 5 | 0.551 ± 0.040 | 0.363 | 0.495 | 0.786 |
| замороженный bert | 5 | 0.554 ± 0.035 | 0.391 | 0.557 | 0.715 ± 0.101 |
| дообученный gpt2 | 3 | 0.587 ± 0.012 | 0.432 | 0.558 | 0.770 |
| **дообученный bert** | 5 | **0.601 ± 0.019** | 0.447 | 0.588 | 0.766 ± 0.025 |

(`route`/`benefit` — средние по сидам; `escalate` у замороженного bert и у
дообученного — с разбросом, потому что там он и прыгает; у замороженного gpt2
это значение опубликованного пака.)

Дообучение даёт **+5.0 п.п.** к замороженному gpt2 и **+4.7 п.п.** к
замороженному bert (Mann–Whitney по сидам: p = 0.016 и 0.028), и вдвое снижает
разброс. Прирост не только в `route` (+5.6 п.п. к замороженному bert) и
`benefit` (+3.1), но и в стабильности `escalate`: у замороженного bert он гуляет
0.715 ± 0.101 (на одном сиде падает до 0.529), у дообученного — 0.766 ± 0.025.
Сам `escalate` при этом так и остаётся около базовой частоты 0.775 — метка
контрфактическая, и по тексту промпта её не вывести.

Проверка на другом домене (AG News, test n=1000): пак на gpt2 — 0.880,
замороженный bert — 0.860, **дообученный bert — 0.900**. То есть дообучение
помогает не только RouterBench, тогда как смена энкодера без дообучения даже
вредит.

Воспроизведение:

```bash
# замороженный энкодер: точность test печатает сам рецепт
DECISION_DEVICE=cuda DECISION_ENCODER_KIND=encoder python -m training.recipe.train_heads --specs routerbench     --encoder bert-base-uncased --dim 768 --limit 4000     --train-steps 500 --val-fraction 0.1 --seed 0     --out-dir /tmp/rb-bert-0

# дообучение энкодера: train/val/test печатает рецепт
DECISION_DEVICE=cuda DECISION_ENCODER_KIND=encoder DECISION_MAX_LENGTH=256 python -m training.recipe.finetune_encoder --specs routerbench     --encoder bert-base-uncased --dim 768 --limit 4000     --steps 300 --lr 5e-5 --seed 0 --out-dir checkpoints/finetune/rb-bert-0
```

Дообученный энкодер опубликован ассетом релиза
[`v0.12.0-encoder-routerbench-bert.tar.gz`](https://github.com/slavabars/decision-cascade/releases/tag/v0.12.0)
(405 МБ: `encoder/`, `heads.pt`, `temperature.json`, `metadata.json`). Он не
входит в `*-weights.tar.gz` с паками голов: энкодер — отдельный артефакт, потому
что весит в сотни раз больше. Рецепт выше остаётся для воспроизведения и для
своего домена.

Примечание: если раннер не на GPU, уберите `--device cuda`; на CPU прогон
заметно дольше (энкодер — узкое место).
