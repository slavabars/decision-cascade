# Стабильность: что значит «выйти из беты» и что для этого нужно

Проект в бете (`0.11.0`). «Бета» здесь означает не «сырой код», а «контракт может
измениться»: API, формат паков и переменные окружения ещё не обещаны надолго.
Ниже — что считается стабильным, по каким критериям мы выходим в `1.0`, и что
для этого осталось.

## 1. Что значит «стабильно» для этого проекта

Три обещания, которые даёт `1.0`:

1. **Контракт API не ломается.** `POST /decisions`, `/decisions/batch`,
   `/v1/systemone`, `/v1/feedback`, `GET /info` и `schema_version = "1"` меняются
   только с повышением major и окном депрекации (2 минорные версии).
2. **Формат артефактов читается.** Пак (`heads.pt` + `metadata.json` +
   `temperature.json`) и чекпоинт `schema_version` читаются всеми версиями
   линейки `1.x`.
3. **Заявленные числа воспроизводятся.** Любая цифра из
   [`benchmarks.md`](benchmarks.md) получается командой из документации на
   Ubuntu 22.04+ с GPU 16 ГБ, а не «у автора на ноутбуке».

Стабильность **не** означает: универсальность (zero-shot), победу над LLM в
открытых доменах или облачный SLA. Это локальный движок решений, и обещание
даётся только про контракт, воспроизводимость и поведение на своём домене.

## 2. Что уже стабильно, а что экспериментально

| Поверхность | Статус | Комментарий |
| --- | --- | --- |
| `/decisions`, `/decisions/batch` | стабильно | схема `schema_version = "1"`, контрактные тесты |
| `/v1/systemone` | стабильно | внешний протокол Jev/TypeSafe, менять нельзя |
| `/v1/feedback` | стабильно (beta-политика) | транспорт фиксирован; смысл зависит от каскада |
| `GET /info` | стабильно | набор ключей расширяется, не сужается |
| Пак `heads.pt` + `metadata.json` + `temperature.json` | стабильно | чтение старых версий обязательно |
| `DECISION_*` переменные из README | стабильно | новые добавляются, старые не меняют смысл |
| Порог уверенности (`DECISION_CASCADE_THRESHOLD`) | стабильно | политика по умолчанию |
| Risk-aware каскад (`DECISION_CASCADE_RISK_BUDGET`) | beta | измерен, но зависит от домена |
| Benefit-каскад (`DECISION_CASCADE_POLICY=benefit`) | beta | новый, нужен `q` и обратная связь |
| Option-scoring голова | beta | перенос вариантов измерен, в паках не используется |
| Дообучение энкодера (`finetune_encoder`) | beta | измерено (+5 п.п.), веса не публиковались |
| `eval/*`, `judge`, скрипты бенчмарков | без гарантий | внутренний инструментарий |

## 3. Критерии выхода в 1.0

Каждый пункт — проверяемый, а не «ощущение зрелости».

| # | Критерий | Сейчас | Что осталось |
| --- | --- | --- | --- |
| 1 | Нет ломающих изменений 3 минорных релиза подряд | 0.10 → 0.11 без ломки | 0.12 + 0.13 без ломки контракта |
| 2 | Опубликована политика депрекации | нет | раздел в этом документе + предупреждения в коде |
| 3 | Контрактные тесты на все эндпоинты и SDK | есть на все эндпоинты | тест «старый пак читается новой версией» |
| 4 | Покрытие `src` + `api` ≥ 90% | **94%** (2000 строк) | гейт в CI (сейчас не проверяется) |
| 5 | CI: ruff, shellcheck, pytest, сборка и smoke установленного wheel | ruff/shellcheck/pytest есть | smoke: установка wheel в чистый venv + один запрос к серверу |
| 6 | Регрессия качества закреплена в CI | `test_competitors_regression.py` на mock | прогон на фиксированных сидах с порогом в ночном job |
| 7 | Репродуцируемость данных | RouterBench закреплён ревизией | закрепить AG News ревизией; lockfile зависимостей |

| 9 | Безопасность: модель угроз, отсутствие PII в логах, аудит зависимостей | `SECURITY.md` есть, auth осознанно нет | запрет логировать `state`/`feedback`, `pip-audit` в CI |
| 10 | Документация: quickstart в чистом окружении, деплой Ubuntu/CentOS, upgrade/rollback | quickstart и деплой есть | проверить upgrade/rollback на реальных скриптах, раздел troubleshooting |
| 11 | Замеры опубликованы с сырыми данными и командами | [`benchmarks.md`](benchmarks.md) + ассеты релизов | — |

Пункты 1, 12 — календарные: их нельзя ускорить кодом, поэтому выход в `1.0`
реалистично через две минорные версии.

## 4. План работ

### P0 — до следующего релиза (контракт и эксплуатация)

1. `/health` и `/ready`: первый отвечает всегда, второй — только когда энкодер и
   головы загружены. Нужны systemd и балансировщикам, сейчас их нет.
2. Таймауты и один retry для `HttpSystemOneBackend` + таймаут на весь запрос:
   молчаливое зависание каскада — худший отказ.
3. Гейт покрытия в CI (`--cov-fail-under=90` для `src`+`api`) и smoke-тест
   установленного wheel (старт сервера + один запрос).
4. Закрепить AG News ревизией; добавить lockfile зависимостей.
5. Запретить логирование `state`, `images` и тел `/v1/feedback`; тест на это.

### P1 — к 1.0 (стабильность контракта)

6. Политика депрекации: срок 2 минорные версии, `Deprecation`-заголовки,
   `warnings` в логах, раздел в CHANGELOG.
7. Тест обратной совместимости паков: пак, собранный в 0.8, читается текущей
   версией (эталонный файл в `tests/`).
8. Ночной job с моделью: фиксированные сиды, порог по accuracy RouterBench/AG
   News, падение при регрессе > 1 п.п.
9. Upgrade/rollback в деплое: сохранить и восстановить пак и `.env`,
   задокументировать, проверить на Ubuntu и CentOS.
10. Troubleshooting: типовые ошибки (`UNTRAINED_HEADS`, `MODALITY_NOT_SUPPORTED`,
    отсутствие `q`, несовпадение `choice_head`).

### P2 — после 1.0

11. Публикация дообученного энкодера ассетом (сейчас 419 МБ — рецепт вместо
    весов; см. `routerbench.md`).
12. Метрики Prometheus и structured logs с request id.
13. Слабая разметка: пак из ответов сильной модели на неразмеченных данных.
14. Многодоменные паки с переключением по подписи вопросов.

## 5. Политика депрекации (черновик, вступает с 1.0)

- Breaking change в API, формате пака или смысле `DECISION_*` — только в major.
- Deprecation объявляется минимум за 2 минорные версии: предупреждение в логах,
  пометка в README и запись в CHANGELOG (`### Deprecated`).
- Минорная версия может добавлять поля ответа и переменные окружения; удалять —
  нет.
- Патч-версия не меняет ни поведения, ни формата.

## 6. Риски, из-за которых можно остаться в бете

1. **Разметка.** Вся ценность начинается после нескольких тысяч размеченных
   примеров на домен. Если это дорого, ниша узкая — отсюда P2 «слабая разметка».
2. **Zero-shot.** Конкуренты работают «из коробки», мы нет. Позиционирование
   обязано это признавать, иначе первое же сравнение без разметки обесценит
   проект.
3. **Дрейф домена.** `q` и температура уточняются обратной связью, но головы
   без новых примеров стареют. Нужен измеренный ответ (дообучение по фидбэку),
   иначе обещание «стабильно» превращается в «стабильно на дате среза».
4. **Один человек.** Автобусный фактор: документация, воспроизводимость и
   артефакты — единственная страховка; поэтому они в критериях выхода, а не «на
   потом».
