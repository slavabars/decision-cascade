# Бюджет латентности: батчинг, длина входа и dtype

Сколько стоит решение и что из этого реально ускоряет — измерено свипом
`eval.latency.sweep`, а не на глаз. Числа получены на одной машине
(Ubuntu 24.04): CPU — общий, GPU — NVIDIA RTX 5060 Ti (драйвер 595.99.02,
CUDA 13.2). Абсолютные значения на CPU шумные, выводы — про порядок величин и
выбор параметров.

## 1. Как меряем

```bash
.venv/bin/python -m eval.latency.sweep \
  --encoder cointegrated/rubert-tiny2 --dim 312 --kind encoder --device cpu \
  --batch-sizes 1,8,16,32,64 --lengths 32,64,128,256 \
  --dtypes float32,bfloat16,float16 --states 64 --n 10 --repeats 3
```

Три важные детали методики:

- **каждый повтор кодирует новые состояния.** `DecisionService` кэширует
  признаки по тексту промпта; с одним и тем же текстом второй замер показывает
  задержку без энкодера (в первой версии свипа так и вышло — 33 000
  состояний/с);
- **длина входа меряется на длинном состоянии** (~700 токенов), иначе обрезка
  до 32 и до 256 токенов даёт одинаковое время;
- батчинг меряется через `decide_many` (путь `/decisions/batch`), а длина и
  dtype — через одиночный `decide` с разными состояниями.

## 2. Батчинг

`DECISION_ENCODE_BATCH` — размер батча энкодера. На коротких состояниях
(3 вопроса на состояние):

| batch | rubert CPU | rubert GPU | gpt2 CPU | gpt2 GPU |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 4.5 | 2.6 | 267.5 | 13.0 |
| 8 | **1.7** | 0.7 | 179.6 | 9.1 |
| 16 | 1.9 | 0.4 | 175.6 | **8.8** |
| 32 | 1.7 | 0.3 | **175.2** | 9.1 |
| 64 | **1.6** | **0.2** | — | — |

Мс на состояние в `decide_many` (3 вопроса). Вывод: батч `>= 8` даёт **2.7×** на
маленькой модели и **1.5×** на gpt2 на CPU; на GPU выигрыш ещё больше —
**12×** у `rubert-tiny2` (2.6 → 0.2 мс) и 1.5× у gpt2. Для `/decisions/batch`
это бесплатно: `DECISION_ENCODE_BATCH=16` — разумный дефолт, `32–64` — если
память позволяет.

## 3. Длина входа

`DECISION_MAX_LENGTH` — главный рычаг на CPU: время почти линейно по токенам.

| max_length | rubert CPU | rubert GPU | gpt2 CPU | gpt2 GPU |
| ---: | ---: | ---: | ---: | ---: |
| 32 | **6.2** | — | — | — |
| 64 | 7.0 | **3.1** | **189.3** | **9.4** |
| 128 | 17.6 | 3.4 | 303.3 | 16.3 |
| 256 | 15.0 | 3.9 | 434.8 | 24.8 |

p50 на одиночный запрос, мс. (У rubert 128 и 256 на CPU в пределах шума —
модель упирается в длину реального состояния, а не в лимит.)

Вывод: обрезка `256 → 64` экономит **2.3×** на gpt2 (CPU и GPU) и до **2.5×**
на маленькой модели. Если задача не требует длинного контекста,
`DECISION_MAX_LENGTH=64` или `128` — самый дешёвый способ уложиться в бюджет.

Для сравнения с продакшен-числами: gpt2 на GPU при `max_length=256` — 24.8 мс
p50 на один запрос с тремя вопросами; это тот же порядок, что в
`docs/benchmarks.md` (10–46 мс).

## 4. dtype

| dtype | rubert CPU | rubert GPU | gpt2 CPU | gpt2 GPU |
| --- | ---: | ---: | ---: | ---: |
| float32 | 13.5 | 3.8 | — | 24.3 |
| float16 | не поддерживается | **3.0** | не поддерживается | **9.6** |
| bfloat16 | **10.3** | **2.9** | — | **9.5** |

p50 на одиночный запрос, мс. Точность голов на 256 примерах (float32 → fp16 /
bf16):

| Пак | float32 | float16 | bfloat16 |
| --- | ---: | ---: | ---: |
| AG News (`public-gpt2`) | 0.8776 | 0.8763 | 0.8763 |
| Русский (`ru-rubert-tiny2`) | 0.7240 | 0.7240 | 0.7266 |

- **GPU: `float16`/`bfloat16` дают 2.5×** на gpt2 (24.3 → 9.5 мс) и 1.3× на
  маленькой модели, точность меняется в пределах ±0.3 п.п. (на 256 примерах
  это шум). Для GPU-деплоя это самый дешёвый выигрыш.
- **CPU: `bfloat16` даёт −24% p50** без изменения точности на проверенной
  выборке; `float16` на CPU не поддерживается — `src/device.py` честно падает с
  подсказкой, а не молча считает в float32.
- Числа — sanity-check на 256 примерах, а не гарантия: проверяйте точность на
  своём домене перед переключением.

## 5. int8: измерено, не внедрено

Прототип `torch.ao.quantization.quantize_dynamic` на rubert-tiny2 (CPU, 64
текста):

| | float32 | dynamic int8 |
| --- | ---: | ---: |
| время кодирования | 393.4 мс | **291.2 мс** (1.35×) |
| косинус эмбеддингов | — | 0.99586 |
| accuracy голов (64 примера) | 0.6719 | 0.6510 |

Решение: **не внедрять**. Ускорение 1.35× не окупает потерю 2 п.п. на
маленькой выборке и поддержку API, который PyTorch помечает как deprecated
(рекомендует `torchao`/pt2e). Если нужен int8 — это отдельная задача с
проверкой точности на полном тесте и выбором бэкенда.

## 6. Что из этого следует

- CPU + `rubert-tiny2`: батч 8–16, `max_length=64–128`, `bfloat16` — единицы
  миллисекунд на состояние в батче и десятки на одиночный запрос.
- CPU + gpt2: ~175 мс/состояние в батче и 190–435 мс на одиночный запрос в
  зависимости от обрезки. Это совпадает с ночным регрессом (p50 300–450 мс на
  трёх вопросах), то есть бюджет `p95 < 1 c` на CPU достижим только с
  обрезкой и батчингом.
- GPU на порядок быстрее (p50 9–25 мс на gpt2 в зависимости от обрезки), и
  `float16`/`bfloat16` — обязательный выбор для GPU-деплоя. Ночной CPU-бюджет и
  продакшен-бюджет — разные числа, путать их нельзя.

## 7. Воспроизведение

```bash
# rubert-tiny2 на CPU: батчи, длина, dtype
.venv/bin/python -m eval.latency.sweep \
  --encoder cointegrated/rubert-tiny2 --dim 312 --kind encoder --device cpu \
  --batch-sizes 1,8,16,32,64 --lengths 32,64,128,256 \
  --dtypes float32,bfloat16,float16 --states 64 --n 10 --repeats 3 \
  --out data/latency/rubert.json --markdown data/latency/rubert.md

# gpt2 на CPU
.venv/bin/python -m eval.latency.sweep \
  --encoder openai-community/gpt2 --dim 768 --kind causal --device cpu \
  --batch-sizes 1,8,16,32 --lengths 64,128,256 --states 64 --n 10 --repeats 3

# то же на GPU, включая dtype
DECISION_DEVICE=cuda .venv/bin/python -m eval.latency.sweep \
  --encoder openai-community/gpt2 --dim 768 --kind causal --device cuda \
  --dtypes float32,float16,bfloat16 --states 64 --n 20 --warmup 3
```
